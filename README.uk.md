# Бронювання переговорних / Meeting Room Booking

**Українська версія** | [English Version](README.md)

Сучасний веб-застосунок для бронювання переговорних в офісі. Реалізований як monorepo на npm workspaces з єдиним продакшн Docker-контейнером, що віддає NestJS API та React SPA, з використанням бази даних PostgreSQL 18 та Drizzle ORM.

---

## 1. Про проєкт та архітектура

Застосунок дозволяє співробітникам переглядати розклад кімнат на інтерактивній тижневій сітці, бронювати вільні 30-хвилинні слоти, керувати своїми майбутніми та минулими бронюваннями, а також отримувати сповіщення в застосунку перед закінченням бронювання, якщо наступний слот зайнятий.

### Структура монорепозиторію

- **`apps/api`**: NestJS 11 (Express-адаптер) застосунок, що обробляє всі backend-роути за префіксом `/api`. Відповідає за аутентифікацію, сесії, кімнати, валідацію бронювань, підтвердження пошти та сповіщення. У продакшні також віддає зібрані статичні файли SPA з фолбеком на `index.html` для deep links.
- **`apps/web`**: React 19 + Vite 8 SPA зі стилізацією на Tailwind CSS v4 (CSS-first підхід). Використовує `@tanstack/react-query` для запитів, `react-router` v8 для навігації та `react-hook-form` із Zod-схемами для форм.
- **`packages/core`**: Спільний пакет доменної логіки. Містить розрахунок робочих годин офісу на Luxon, генератори слотів тижневої сітки, утиліти роботи із часовими поясами (DST-aware) та спільні Zod-схеми валідації.

### Технологічний стек

| Шар | Технології |
|---|---|
| Фреймворки | NestJS 11, React 19, Vite 8 |
| Стилізація | Tailwind CSS v4 |
| База даних та ORM | PostgreSQL 18, Drizzle ORM (`drizzle-orm@0.45.2`, `drizzle-kit@0.31.10`) |
| Валідація та дата/час | Zod v4, Luxon v3 |
| Менеджер пакетів | npm workspaces (Node.js >= 24) |

## 2. Швидкий запуск через Docker Compose (Рекомендовано)

Запуск усього застосунку (база даних PostgreSQL 18 + NestJS API + React SPA) однією командою з чистої машини:

```bash
cp .env.example .env
docker compose up --build
```

### Точки доступу
- **Веб-застосунок (SPA):** [http://localhost:3000](http://localhost:3000)
- **Перевірка здоров'я API (Health Check):** [http://localhost:3000/api/health](http://localhost:3000/api/health)

### Автоматична ініціалізація
Під час старту контейнера автоматично виконуються:
1. Застосування міграцій бази даних (`apps/api/dist/db/migrate.js`).
2. Заповнення початковими даними / сідами (кімнати, тестові користувачі, демо-бронювання) ідемпотентним способом.

Для перезапуску або скидання стану контейнерів:
```bash
docker compose down && docker compose up
```

## 3. Локальна розробка (Без Docker)

### Вимоги
- Node.js >= 24
- Запущений локальний PostgreSQL 18

### Покрокова інструкція

1. **Налаштування оточення:**
   Скопіюйте `.env.example` у `.env` та відкоригуйте параметри підключення до PostgreSQL за потреби:
   ```bash
   cp .env.example .env
   ```

2. **Встановлення залежностей:**
   ```bash
   npm install
   ```

3. **Збірка пакетів монорепозиторію:**
   Компілює `@booking/core`, `@booking/web`, `@booking/api` та копіює артефакти веб-збірки:
   ```bash
   npm run build
   ```

4. **Запуск серверів розробки:**
   - **Термінал 1 (API Сервер):**
     Запускає NestJS у режимі watch та автоматично виконує міграції і сіди при старті:
     ```bash
     npm run dev:api
     ```
   - **Термінал 2 (Web SPA Dev Сервер):**
     Запускає dev-сервер Vite з підтримкою гарячої перезагрузки (HMR):
     ```bash
     npm run dev:web
     ```
     Відкрийте [http://localhost:5173](http://localhost:5173) у браузері.

5. **Генерація нових міграцій (Drizzle):**
   У разі зміни схеми в `apps/api/src/db/schema.ts` згенеруйте нову міграцію командою:
   ```bash
   npm run db:generate
   ```

## 5. Механізм роботи сідів (Seed Data)

Сіди запускаються автоматично при старті API (`npm run dev:api` або під час запуску Docker-контейнера), а також можуть бути викликані вручну командою `npm run db:seed -w apps/api`.

Усі операції сідування використовують SQL `ON CONFLICT DO UPDATE` (апсерт за унікальним ключем або фіксованим UUID), що гарантує повну ідемпотентність і запобігає дублюванню даних при повторних запусках:

- **6 Переговорних кімнат:**
  - **Дуб** (Поверх 2, Місткість 12, Зручності: Проєктор, маркерна дошка)
  - **Ясен** (Поверх 2, Місткість 8, Зручності: ТВ 55", вебкамера)
  - **Липа** (Поверх 3, Місткість 4, Зручності: Тиха кімната для дзвінків)
  - **Верба** (Поверх 3, Місткість 6, Зручності: ТВ, фліпчарт)
  - **Сосна** (Поверх 4, Місткість 16, Зручності: Конференц-звук, трансляція)
  - **Клен** (Поверх 4, Місткість 4, Зручності: Фокус-кімната)
- **2 Тестові користувачі:** Створюються з фіксованими UUID та хешованими паролями bcrypt, з позначкою підтвердженої пошти (`emailVerifiedAt = NOW()`).
- **7 Демо-бронювань:** Динамічні дати відносно моменту запуску — 5 майбутніх бронювань, розподілених по поточному тижню за Києвом, та 2 минулих бронювання на попередній тиждень. Це гарантує, що вкладки «Майбутні» та «Минулі» на сторінці «Мої бронювання» (`/my-bookings`) завжди заповнені, незалежно від дня перевірки.

## 6. Запуск тестів

У проєкті реалізовано юніт-тести, інтеграційні тести API та E2E тести.

### Юніт-тести
Запускає юніт-тести для `@booking/core`, `@booking/web` та `@booking/api` (включаючи розрахунок слотів Luxon, Zod-валідації, логіку фільтрації за місткістю та тести компонентів React). Не потребує запущеної бази даних PostgreSQL.
```bash
npm test
```

### Інтеграційні тести API
Потребує доступного сервера PostgreSQL — підніміть його командою `docker compose up -d db` (або використайте власний локальний інстанс за зразком `.env.example`). Сюіт (`apps/api/test/bookings.int-spec.ts` та `notifications.int-spec.ts`) сам створює і мігрує базу `booking_test` під час першого запуску, тож окрема ручна підготовка бази не потрібна — достатньо піднятого Postgres. Перевіряє реальні HTTP-запити аутентифікації, створення бронювань, бронювання впритул, 409 конфлікти перетинів, 403 авторизаційні обмеження, потік підтвердження пошти, скасування серії та сповіщення.
```bash
docker compose up -d db
npm run test:integration
```

### E2E тести API
Запускає E2E тести NestJS (`apps/api/test/health.e2e-spec.ts`), що перевіряють роут `/api/health`, повернення JSON 404 для неіснуючих API-маршрутів та fallback на HTML SPA для глибоких посилань:
```bash
npm run test:e2e -w apps/api
```

## 7. Підтвердження email у dev-режимі

У dev-режимі реальний SMTP-сервер замінено на вивід посилань у консоль сервера:

1. **Реєстрація користувача:** При реєстрації акаунта через `/register` створюється унікальний токен, а посилання підтвердження виводиться в stdout сервера (`docker compose logs api` або Термінал 1):
   `http://localhost:3000/verify/<token>`
2. **Проходження підтвердження:** Перехід за посиланням відкриває екран підтвердження в SPA, який надсилає `POST /api/auth/verify/<token>` і позначає пошту підтвердженою.
3. **Серверний захист:** Непідтверджені акаунти не можуть створювати бронювання (`POST /api/bookings`) — сервер повертає HTTP `403 Forbidden` (`"Для створення бронювання необхідно підтвердити пошту"`).
4. **Повторна відправка:** Залогінений користувач із непідтвердженою поштою може натиснути «Надіслати ще раз» у банері (`POST /api/auth/verify/resend`), щоб згенерувати нове посилання. Термін дії токена — 24 години.

## 8. Реалізовані бонусні пункти з §05

Усі додаткові бонусні пункти з розділу §05 специфікації `reference/task-spec.md` повністю реалізовані:

1. **Docker Compose:** Конфігурація підйому однією командою (`docker compose up --build`), що збирає SPA та Nest API в один контейнер поруч із PostgreSQL 18 з автоматичними міграціями та сідуванням.
2. **Підтвердження Email у dev-режимі:** Вивід посилання підтвердження в лог сервера; блокування створення бронювань на сервері (403) до підтвердження пошти.
3. **Щотижневі повторювані бронювання:** Можливість створення серій бронювань (від 2 до 52 повторень) із підтримкою скасування як одного повторення, так і всієї серії.
4. **Захист від гонки (Race Protection):** PostgreSQL GiST exclusion constraint (`bookings_no_overlap`) на `(room_id, tstzrange)` атомарно запобігає подвійному бронюванню на рівні БД (повертає 409).
5. **Сповіщення про закінчення бронювання:** Тости та сповіщення в дзвіночку попереджають автора за `NOTIFY_BEFORE_MINUTES` (за замовчуванням 10) хвилин до кінця, якщо наступний слот зайнятий.
6. **Інтеграційні тести API:** Автоматизований сюіт інтеграційних тестів (`npm run test:integration`), що тестує HTTP API для auth, валідацій, race condition, скасування серій та сповіщень.
7. **Фільтр кімнат за місткістю:** Інтерактивний фільтр місткості (`Будь-яка` та чипи `від N`) на сторінці вибору кімнат. Пороги обчислюються з фактичних місткостей наявних кімнат, а не зі сталого списку — тож жоден чип не веде в порожній результат або нічого не змінює.
8. **Повноцінний мобільний сценарій:** Адаптивний інтерфейс із виділеним пейджером одного дня (`MobileDayPager`) на малих екранах та зручними сенсорними контролами.

## 9. Як влаштована перевірка перетинів і як зберігається час

### Перевірка перетинів

Перевірка перетинів бронювань реалізована на рівні бази даних PostgreSQL за допомогою обмеження виключення GiST (`bookings_no_overlap`): `EXCLUDE USING gist (room_id WITH =, tstzrange(starts_at, ends_at, '[)') WITH &&) WHERE (canceled_at IS NULL)`. Напіввідкритий інтервал `[)` гарантує, що суміжні бронювання (наприклад, 10:00–11:00 та 11:00–12:00) не конфліктують, а частковий індекс `WHERE (canceled_at IS NULL)` дозволяє скасованому бронюванню одразу звільнити слот. Застосунок не бере жодних блокувань (`SELECT FOR UPDATE`) — він покладається на сам constraint: при спробі подвійного запису PostgreSQL повертає помилку виключення (SQLSTATE `23P01`), яку сервіс перетворює у відповідь HTTP 409 (`Слот зайнятий`). Саме це робить паралельні однакові запити безпечними: обидва можуть пройти валідацію, але вставку в базу завершить лише один. Валідація в Zod-схемах (`packages/core/src/domain/overlap.ts`) додатково відсікає очевидно конфліктні запити ще до звернення до бази, тож типовий випадок отримує швидку зрозумілу помилку, а не чекає на конфлікт у БД.

### Збереження часу та часові пояси

Кожен момент часу (`starts_at`, `ends_at`, `created_at`, `canceled_at`, `email_verified_at`) зберігається як `timestamptz` в UTC — ніде не зашитий літеральний київський зсув. Робочі години (09:00–19:00) та сітка тижня рахуються відносно `Europe/Kyiv` через Luxon у `@booking/core`, тому що зсув Києва змінюється разом із європейським переходом на літній час, а пояс глядача може перейти на інший режим в інший день. Браузер показує кожен час у поясі глядача (`Intl.DateTimeFormat().resolvedOptions().timeZone`); якщо він відрізняється від київського, інтерфейс показує банер із поточним зсувом офісу, а серверна валідація (робочі години, межі слотів) завжди рахується за київським часом для конкретного моменту.
